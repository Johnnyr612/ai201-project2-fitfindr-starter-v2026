# Acceptance criteria — FitFindr

Five criteria that say what "working" means for this agent, written in unit 3
**before** any results existed.

An acceptance criterion names a target: a number, a count, a rate, or something
a person could plainly observe. *"The agent handles errors"* is an opinion.
*"When search returns nothing, the agent stops before calling the second tool,
in 5 of 5 tries"* is a criterion.

Under each one, write a sentence or two on **why that target** and not a
stricter one. A reason that says something about your tools, your loop, or the
data earns credit; *"80% seemed reasonable"* does not.

> Missing your own targets next unit costs you nothing. Setting a target so
> easy you can't miss it does.

**Two are written for you. You write three.**

---

## 1. A matching query completes all three tools

Given a query that matches at least one listing, the agent completes all three
tool calls and returns a fit card — in at least 4 of 5 tries.

**Why this target:**
The search depends on matching words in a natural-language query to listing
text, so a relevant phrasing may occasionally be missed. Four successful runs
out of five checks that the full tool sequence usually works while allowing
for that search variability.

---

## 2. An impossible query stops before the second tool

Given a query that matches no listings, the agent stops before calling
`suggest_outfit` and returns a message naming what to change — 5 of 5 tries.

**Why this target:**
This path has a clear deterministic condition: when search returns no listings,
the loop should stop before calling `suggest_outfit`. The helpful message is
also controlled by the agent rather than generated by a model, so it should
work in every run.

---

## 3. The selected item reaches the outfit tool

For a query that finds an item, `session["selected_item"]["id"]` matches the
`new_item["id"]` passed to `suggest_outfit` in 5 of 5 runs.

**Why this target:**
The item handoff is controlled by the agent's session logic, not by model
wording, so it should be consistent in every run. Comparing IDs makes the
handoff directly observable.

---

## 4. Fit cards include the important details

In at least 4 of 5 runs, the fit card is 2 to 4 sentences and mentions the
item, its price, and its platform once each.

**Why this target:**
These details make the caption useful as a post about the actual listing.
The model's wording varies, so allowing one miss out of five is realistic
without making the content requirements vague.

---

## 5. Search respects the price ceiling

For a query with an inclusive `max_price`, every returned listing costs at or
below that ceiling in 5 of 5 runs.

**Why this target:**
A price ceiling is a clear constraint users rely on. This is a deterministic
numeric filter, so it should pass every run rather than being allowed a
model-variability margin.
